## 요약

이번 범위는 P1(회의록 수집·정리)과 P2(단계 길잡이)다. 2026-11-03 논의에서 결정 13개를 확정했다. 단계 판정은 정답지가 없어 가정으로 두고 진행하면서 고친다. P1·P2는 아직 구현하지 않았고, 그 전 작업은 모두 main에 들어갔다(PR #1, #2).

보고서(md)와 비교해 크게 바뀐 점은 네 가지다.

- **새 회의록은 사람이 한 번 확인한 뒤 반영한다.** 봇이 미리 추출해 두고, 팀원 누구나 미리보기를 확인하면 들어간다. 이미 확인된 회의록이 수정되면 자동으로 반영한다.
- **단계 전환은 승인을 받는다.** 봇은 게이트 충족 여부를 보고 제안만 하고, 관리자·개발자가 승인한다. 회의 차수를 단계에 대응시키는 방식은 버렸다. 이 팀은 회의를 세 번 했지만 실제로는 1-2 단계다.
- **부분은 최상위 블록 단위로 나눈다.** 제목 기준으로는 1차 멘토링 토글 안의 기획서(약 14,500자)를 떼어 낼 수 없었다.
- **회의록 입구가 늘었다.** Notion에 더해 Teams 채팅(붙여넣기·파일)과 클로바노트에서 내려받은 파일로도 받는다.

## 목표와 성공 기준

**목표**: 팀이 회의록을 따로 정리하지 않아도, 봇이 회의에서 나온 결정·할 일·피드백을 빠짐없이 모으고 문서와 섞지 않는다. 그 위에서 팀 전체에 지금 단계와 넘어가기 전에 비어 있는 것을 알려 준다. 게이트 질문·단계 전환·되돌리기는 관리자·개발자(그리고 관리자가 권한을 준 사람)가 답한다.

| # | 성공 기준 | 확인 방법 |
| --- | --- | --- |
| 1 | 회의 추출에 빠진 것·틀린 것이 없다 | 봇이 1~3차 멘토링 추출 초안을 만들고, 송지원이 고친 것을 정답지로 삼아 비교 |
| 2 | 문서 내용이 추출 결과에 섞이지 않는다 | 1차 멘토링의 `구체화` 기획서가 문서로 판정되고 추출에서 빠진다 |
| 3 | 이 팀을 1-2로 본다 | 1-3이라고 단정하지 않고 "주제 확정"을 빈 게이트로 제안한다 |
| 4 | 메뉴를 누를 때 Groq를 부르지 않는다 | 메뉴 응답 로그의 Groq 호출 수 0 |
| 5 | VOC·개발 단계 판정 | **가정으로 진행.** 정답지가 없어 게이트 기본값을 가정으로 두고, 진행할 때마다 로그·데이터 흐름을 근거로 테스트를 먼저 써서 고친다 |

## 목표 구조

입구가 어디든 같은 흐름을 탄다. Notion은 읽기만 하고, 메뉴는 저장본만 읽는다.

1. **입구**: Notion 페이지(md 1회·블록 대조), Teams 채팅(붙여넣기·파일), 클로바노트(작성자가 내려받은 파일·텍스트)
2. **부분 나누기**: 최상위 블록 단위, 내용 해시
3. **종류 판정**: 메모·문서·링크, 특이 구조도 감지
    - 문서 → **문서 보관**: 한 줄 설명, 1번 메뉴 링크
    - 메모·피드백 → 4번으로
4. **부분별 추출**: Groq 1회, 해시로 저장
5. **확인 대기** *(사람이 답함)*: 미리보기, 팀원 누구나
6. **worklog 반영**: 자동 대체, 되돌리기
7. **단계 제안**: 게이트 충족 여부
8. **권한자 승인** *(사람이 답함)*: 관리자·개발자
9. **메뉴 1~4번**: 저장본만 읽음

사람이 답하는 곳은 두 군데다. 새 회의록 미리보기는 팀원 누구나 확인하고, 단계 전환은 권한자가 승인한다. 그 밖의 결정 대체, 확인된 회의록의 수정 반영은 자동으로 하고 알림만 준다.

## P1 설계: 회의록 수집·정리

P1이 끝나면 회의록은 부분 단위로 저장된다. 메모·피드백 부분만 한 번 추출하고, 사람이 확인한 뒤 worklog에 들어간다. 파일·함수 이름은 지금 코드 기준이고, 새 모듈 이름은 가칭이다. 상세 규격은 [spec.md](spec.md)에 있다.

### P1-1 수집 (결정 1·2)

- 새 `notion_md.fetch_markdown(client, page_id)`
    - `notion_read` 관문을 지나고, 이 호출에만 `Notion-Version: 2026-03-11`을 넣는다.
    - `truncated`가 true면 `unknown_block_ids`로 이어 받는다. 페이지당 호출 상한을 둔다.
- 들여쓰기 없는 줄을 최상위 항목의 시작으로 보고 md를 자른다.
- 구조 지문을 만들려고 이미 받는 `notion_map.top_blocks` 목록과 개수·순서를 대조해 부분마다 블록 ID를 붙인다. 어긋나면 그 페이지만 기존 블록 읽기(`notion_read._block_text`)로 돌아간다.
- 수정 시각 비교(`source_units`)는 그대로라, 안 바뀐 페이지·행은 md도 받지 않는다.
- link_to_page는 하위 페이지처럼 따라간다.

### P1-2 종류 판정과 특이 구조 감지 (결정 1·3)

- 바뀐 페이지마다 Groq를 한 번 부른다. 입력은 부분별 경로, 길이, 앞 200자, 하위 항목 개요(경로·길이·토글 여부)다.
- 출력은 부분별 종류(`meeting` / `document` / `link`), 확신, 문서의 한 줄 설명이다. 더해서 "이 부분 안의 하위 항목은 문서다"라는 목록을 받아 그 하위 항목을 따로 떼어 낸다.
- 예상 결과: 1차 멘토링의 `스마트 옷장`은 `meeting`, 그 안의 `구체화` 토글은 `document`("스마트 옷장 기획서, 9/28 기준").
- 내용 해시가 같으면 다시 판정하지 않는다. 사람이 `map-set`으로 정한 종류는 블록 ID에 묶어 유지한다.

### P1-3 추출

- 대상은 `meeting` 부분만이다.
- 항목은 결정, 할 일(담당·기한), 미정, 피드백, 인사이트다. 항목마다 원문 인용과 확신을 받는다.
- (내용 해시, 프롬프트 버전)을 키로 저장해 재시작해도 다시 보내지 않는다.
- 같은 항목 합치기는 코드가 한다. 한 부분이 분당 한도를 넘으면 하위 항목에서 나눠 보낸다.

### P1-4 반영 흐름 (결정 7·8-1)

회의록 부분은 `추출됨 → 확인 대기 → 반영됨` 상태를 거친다.

1. **직접 반영**: 4번 ② "Notion 변경 반영"에서 최근 수정된 페이지를 고른다. 봇이 지금 읽고 추출해 미리보기를 보여 준다. [반영] / [고치기] / [취소] 중에서 고른다.
2. **자동 감지**: 새 회의록을 찾으면 미리 추출만 해 둔다. 마지막 수정 후 2시간이 지나면 메인 카드에 "새 회의록 n건 확인 대기 [확인하기]"를 띄운다. 누구든 확인하면 반영된다.
3. **[고치기]**: 항목을 지우거나 고치거나 더한다. 고친 내용은 따로 저장해 추출 정답지(성공 기준 1)로 쓴다.
4. **확인된 회의록이 수정되면**: 다시 추출해 바뀐 항목만 자동으로 반영하고 알린다. 항목이 그대로면 조용히 넘어간다.
5. **삭제되면**: 회의록 부분이 사라지면 거기서 나온 항목을 지울지 권한자에게 묻는다. 소스 페이지(팀 정보·문서)는 수정·삭제 모두 권한자에게 묻는다.

### P1-5 worklog (결정 4)

- 확인된 항목은 기존 `worklog/core.py`의 정규화·판정을 거쳐 바로 반영한다. 확인한 사람을 반영자로 남긴다.
- 기존 결정을 대체한다고 판정되면 자동으로 대체하고 메인 카드에 "A → B [되돌리기]"를 띄운다. 확신이 낮거나 판정에 실패하면 "추가 논의 필요"로 보낸다.
- 새 `revert()`는 `revisions`의 이전 스냅샷으로 되돌린다. 권한자만 쓴다.
- 항목 종류에 피드백과 인사이트를 더한다. 처음 수락 기준 4번("AI 판단은 후보일 뿐")을 바꾼 사유를 명세에 남긴다. 건별 승인은 없애되, 새 회의록마다 한 번은 확인한다.

### P1-6 회의록 입구 (결정 10·10-1)

- **Notion**: 설정에서는 팀 정보 페이지만 받는다(6단계 제거). 첫 수집 뒤 "회의록 n건을 찾았어요"를 알리고, 0건이면 "회의록이 다른 곳에 있나요? [소스 추가]"를 띄운다. 이미 회의록 페이지가 등록된 팀은 그대로 쓴다.
- **Teams 채팅**: "회의록 올리기"에서 붙여넣은 텍스트나 파일(txt·docx)을 받는다. 받은 내용은 md로 바꿔 Notion과 같은 부분·추출·미리보기 흐름을 탄다.
- **클로바노트**: 작성자가 내려받은 파일이나 복사한 텍스트를 Teams 채팅으로 받는다. 공유 링크는 읽지 않는다(남은 사항과 위험 참고).

### P1-7 메뉴 1·2번

- 2번은 저장된 추출 결과만 읽는다. Groq 호출은 0회다(성공 기준 4).
- 1번에는 주요 문서 링크와 한 줄 설명을 더한다.
- "(Notion 기준 MM/DD)"는 마지막으로 확인한 시각으로 바꾼다. 지금은 내용이 마지막으로 바뀐 시각이다.

### P1-8 Groq 대기열 (결정 12)

- 순서: [반영] 요청 → 자동 감지 추출(최근 것부터) → 단계 판정(오래된 것부터, P2).
- Groq 응답 헤더(남은 토큰·리셋 시각)로 속도를 맞춘다. 백그라운드는 하루 한도의 일부(예: 70%)까지만 쓴다.
- 한도에 걸리면 "n초 뒤 이어서 정리해요" 또는 "내일 다시 정리돼요. 원문은 저장했어요"라고 알린다. 대기 중인 건수는 "n건 정리 중"으로 보여 준다.
- 응답의 사용량을 저장해 실제 토큰을 잰다. gpt-oss-20b로 바꿀지는 정답지와 비교해 정한다.

### P1-9 이 팀 이전

- 저장소를 백업하고 md로 다시 수집한다. 기존 `sources` 원문은 지우지 않는다.
- "판정 못 함"(`role_source='none'`) 섹션을 다시 판정한다.
- 1~3차 멘토링 추출 미리보기를 만들고, 송지원이 [고치기]로 다듬어 첫 정답지를 만든다.

## P2 설계: 단계 길잡이

봇은 단계를 판정하지 않고 제안한다. 단계가 바뀌는 것은 권한자가 승인했을 때뿐이다.

### P2-1 게이트 기본값 (결정 5-1)

모든 팀이 이 조건으로 시작하고, 권한자가 팀별로 더하거나 빼거나 고친다. 충족 여부는 반영된 worklog 항목(결정·할 일)과 GitHub으로 코드가 판정한다.

| 세부 단계 | 끝났다고 볼 조건 |
| --- | --- |
| 1-1 문제 탐색 | 후보 주제가 1개 이상이고, 후보마다 해결할 문제가 있다 |
| 1-2 방향 확정 | 주제 확정 결정이 있고, 해결할 핵심 문제가 정해졌다 |
| 1-3 구체화·타당성 | 검증할 핵심 가정과 타깃 고객이 정해졌다 |
| 2-1 VOC 설계 | 검증 방법(인터뷰·설문 등)과 대상이 정해졌다 |
| 2-2 수집 | 수집 결과가 기록됐다 |
| 2-3 분석·반영 | 가정 검증 결과와 기능 우선순위가 정해졌다 |
| 3-1 백로그 | GitHub에 백로그 이슈가 있다 |
| 3-2 설계 | 아키텍처 결정이 있다 |
| 3-3 스프린트 반복 | 마일스톤별 진행이 기록된다 |
| 3-4 릴리스·검증 | 릴리스 기준과 충족 여부가 기록됐다 |

VOC는 건너뛸 수 있고, 스프린트는 GitHub 마일스톤으로 본다. 피벗(VOC가 가정을 뒤집으면 기획으로)도 같은 제안 → 승인 흐름을 탄다.

### P2-2 단계 제안과 승인 (결정 5)

| 상황 | 메인 카드 질문 | 답 |
| --- | --- | --- |
| 게이트가 비어 있음 | "현재 1-2단계예요. 주제 확정만 하고 넘어갈까요?" | [정할게요] / [나중에] |
| 게이트를 다 채움 | "1-2단계에서 정할 사안을 완료했어요. 다음 단계로 넘어갈까요?" | [넘어갈게요] / [아직이요] |
| 회의록상 이미 다음 단계인데 게이트가 비어 있음 | "이미 1-3 내용을 논의하고 있는데 주제 확정이 없어요." | [정할게요] / [나중에 할게요] → "이전 단계에서 남은 것" / [건너뛰기] → 목록에서 제외 |

- 같은 질문은 다시 하지 않는다. 단계 판정에 쓸 "지금 논의 중인 단계"는 반영된 항목을 오래된 것부터 Groq로 읽어 판정한다(P1-8 대기열의 마지막 순서).
- 이 팀의 예상값: 후보 주제는 있고 주제 확정은 없음(기획서: "팀 주제 후보") → 1-2, 빈 게이트는 "주제 확정"(성공 기준 3).

### P2-3 권한과 처음 등록 (결정 8·9)

| 할 일 | 할 수 있는 사람 |
| --- | --- |
| 보기(메뉴 1~3, 알림 내용) | 팀 전체 |
| Notion 변경 반영, 회의록 미리보기 확인, 회의록 올리기 | 팀 전체 |
| 단계 전환·게이트 답·되돌리기·삭제 확인·게이트 편집 | 관리자, 개발자, 관리자가 권한을 준 사람 |
| 설정, 권한 부여, 관리자 추가·이전 | 관리자 |

- 관리자는 설정 마법사를 끝까지 마친 첫 사람이다.
- 처음 쓸 때 역할(기획/디자인/개발/기타, 필수) → GitHub 아이디 → 별칭 순서로 묻는다. 뒤의 둘은 건너뛸 수 있고, 3번 메뉴를 처음 누를 때 다시 묻는다.
- 역할·별칭은 사람 단위로 저장해 팀이 달라도 같이 쓴다. 관리자는 역할을 고칠 수 있다.

### P2-4 메인 카드와 감지 (결정 6·8)

- 알림 내용은 모두에게 보인다. 승인 버튼은 권한자에게만 보이고, 나머지에게는 "확인 대기 중"으로 보인다. 회의록 확인 버튼은 모두에게 보인다.
- 알림 종류: 새 회의록 확인 대기, 반영·대체된 항목, 단계 제안, 게이트 질문, 삭제·소스 변경 확인, "n건 정리 중".
- 감지는 챗봇을 열 때(10분 캐시)와 1시간마다 수정 시각만 확인하는 주기 작업 두 가지다. 지금의 1시간 주기 전체 동기화는 수정 시각 확인으로 가볍게 바꾼다.

### P2-5 메뉴 구성 (결정 11)

- **2번 진행상황**: 현재 단계 / 확정된 흐름(대체 이력 포함) / 지금 진행 중 / 이전 단계에서 남은 것 / 추가 논의 필요 / 천천히 정해도 되는 것, 끝에 "(MM/DD 기준)".
- **3번 내 역할**: 내가 맡은 일(GitHub 배정 이슈 + 별칭으로 찾은 회의록 속 일), 그 아래 담당 없는 일 중 내 역할에 맞는 것을 [내가 맡기]와 함께.
- **4번 작업 공유·반영**: ① 완료한 작업 공유(GitHub Project → Done) ② Notion 변경 반영(P1-4) ③ 최근 반영 내역(되돌리기) ④ 회의록 올리기(채팅·파일) ⑤ 소스 추가.

## 남은 사항과 위험

단계 판정은 정답지가 없어 게이트 기본값을 가정으로 두고 진행한다. 진행할 때마다 로그와 데이터 흐름을 근거로 테스트를 먼저 쓰고 고친다. 클로바노트 공유 링크는 확인을 마쳤다.

| 항목 | 내용 | 다음 행동 |
| --- | --- | --- |
| **가정으로 진행**: 단계 판정 정답지 | 이 팀은 1-2라 VOC·개발·피벗을 검증할 수 없음 | 단계마다 로그·데이터 흐름으로 테스트를 쓰고 기본값을 고침. 실제 자료가 생기면 정답지에 더함 |
| **확인 완료**: 클로바노트 공유 링크 | 공개 API 없음. robots.txt가 첫 화면 외 전부를 막음(`Disallow: /`). 공유 페이지는 비밀번호를 넣은 뒤 내부 API로 내용을 불러오는 앱 화면이라, 읽으려면 내부 API를 흉내 내야 함. 공유받은 사람은 다운로드도 못 하고 작성자만 가능 | 링크는 읽지 않음. 작성자가 내려받은 파일이나 복사한 텍스트를 Teams로 올림 |
| 최상위 블록 대조 | md에 블록 ID가 없어 개수·순서로 맞춤. 빈 블록·표·동기화 블록에서 어긋날 수 있음 | 이 팀 페이지 전부로 대조 테스트, 어긋나면 블록 읽기 |
| md API 버전 | `2026-03-11` 헤더로 동작 확인. 다른 호출은 지금 버전 유지 | 이 호출에만 헤더 지정 |
| 확인 대기가 쌓임 | 새 회의록은 사람이 확인해야 반영돼, 아무도 안 누르면 기록이 멈춤 | 메인 카드에 계속 표시. 오래 쌓이면 관리자에게 알림 |
| Teams 파일 받기 | 개인 채팅은 앱 설정에 파일 지원을 켜야 하고, 채널·그룹 채팅의 파일은 SharePoint 링크로 와서 추가 권한이 필요할 수 있음 | 4번 브랜치에서 확인. 안 되면 붙여넣기만 |
| Groq 하루 한도 | gpt-oss-120b 무료 등급 하루 20만 토큰, 조직 단위 | 문서는 추출하지 않음, 20b는 정답지로 비교 |
