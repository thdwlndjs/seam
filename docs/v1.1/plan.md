2026-11-03 · 송지원

## 진행 원칙

1. **테스트를 먼저 쓴다.** 새 테스트는 고치기 전 코드에서 실패하는 것을 확인한 뒤 구현한다. 기존 테스트는 계속 통과해야 한다(시작 77개, spec P1-0으로 없앤 기능의 테스트는 지우거나 바꾸고 PR에 남긴다).
2. **정답이 없는 것은 가정으로 시작한다.** 게이트 기본값과 단계 판정은 [spec.md](spec.md)의 기본값(**[가정]** 표시)으로 시작한다. 아래 "가정으로 진행하는 것의 수정 절차"로 고친다.
3. **실제 Notion으로 확인한 뒤 합친다.** 단위 테스트는 녹화한 응답(fixture)으로 돌리고, 브랜치를 합치기 전에 이 팀 페이지로 한 번 돌려 본다.
4. **브랜치·커밋 규칙**: GitHub Flow(main에서 브랜치 → PR → merge commit)와 Conventional Commits(`feat(server): …`, `fix(bot): …`, `test(…)`, `docs(…)`)를 따른다. 커밋과 푸시는 요청이 있을 때만 한다.
5. **비밀값을 남기지 않는다.** `src/team_configs.json`, `.env`, `src/worklog.sqlite3`, 로그는 커밋하지 않는다. fixture에 들어가는 원문에서 토큰·비밀번호(예: 클로바노트 공유 비밀번호)는 지운다.
6. **phase 문서와 spec을 같이 고친다.** 구현하면서 규격이 바뀌면 spec을 먼저 고치고, phase 문서는 spec 절을 가리키기만 한다.

## 가정으로 진행하는 것의 수정 절차

단계 판정과 게이트 기본값은 정답지가 없다(성공 기준 5). 아래 절차로 고친다.

1. 실제 사용이나 Playground 확인에서 판정이 이상한 경우를 로그로 찾는다. `stage_judge` 로그에 판정 입력(반영된 항목 목록)과 결과(단계·게이트별 참/거짓·근거 ID)가 남는다.
2. 그 입력을 fixture로 옮기고, 기대 결과를 적은 테스트를 먼저 쓴다.
3. 게이트 조건이나 판정 규칙을 고쳐 테스트를 통과시킨다.
4. spec의 게이트 표와 변경 이력에 바꾼 내용과 근거 로그를 적는다.

## 검증 방법

| 종류 | 무엇을 | 언제 |
| --- | --- | --- |
| 단위 테스트 | 분할·대조·상태 전이·권한·게이트 판정 | 매 커밋 |
| fixture 테스트 | 녹화한 md·블록 응답, 가짜 Groq 응답으로 전체 흐름 | 매 커밋 |
| 실제 Notion 확인 | 이 팀 페이지로 수집·추출·메뉴 | 브랜치를 합치기 전 |
| Playground 확인 | 카드 버튼, 미리보기, 권한별 화면 | Phase 3·4·5를 합치기 전 |
| 계측 비교 | Notion·Groq 호출 수, 토큰, 응답 시간 | Phase 1·2를 합치기 전 (Phase 0 기준값과 비교) |

테스트 실행: `src/server`에서 `GROQ_API_KEY= ../../.venv/Scripts/python.exe -m unittest discover -s tests -p "test_*.py"`. `BOT_SERVER_SECRET`은 덮어쓰지 않는다(테스트가 `test-secret`을 기대함).
