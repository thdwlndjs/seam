## 1. 기획 요약

### 1.1 제품 정의

AI PM v2.1은 Microsoft Teams를 기본 인터페이스로 사용하며, Notion에 흩어진 회의·기획·조사·디자인·개발 산출물과 GitHub 작업 상태를 연결해 **프로젝트의 현재 맥락을 설명하고 팀의 다음 의사결정과 협업을 지원하는 AI 프로젝트 매니저**다. 자동으로 결론을 확정하거나 팀에 절차를 강제하는 시스템이 아니다.

기획의 중심은 다음 세 가지 질문이다.

1. **현재 무엇이 정해졌고, 무엇이 진행 중인가?** 최근 산출물·결정·작업 사실을 근거와 함께 설명한다.
2. **왜 그렇게 이해하거나 판단했는가?** 원문 위치, 수정 이력, 검색 범위와 아직 확인되지 않은 부분을 보여준다.
3. **다음에 팀이 무엇을 함께 정하거나 실행해야 하는가?** 지금/나중/역할 간 논점을 분리하고, 사람의 검토·승인 후 업무 시스템에 반영한다.

### 1.2 제품 가치 및 비목표

| 해결하려는 문제 | 목표 사용자 가치 | 비목표 |
| --- | --- | --- |
| 회의 이후 결정·가안·요구사항이 문서 사이에 흩어짐 | 이전 논의부터 현재 상태까지 근거를 따라 확인 | Notion을 완벽한 정답 DB로 전제 |
| 동일한 배경 설명과 담당자 확인이 반복됨 | 팀원 누구나 질문으로 관련 내용과 미확인 범위를 조회 | 답변을 무조건 확정 사실로 판정 |
| 부서·역할 간 의존 작업이 뒤늦게 발견됨 | 지금 합의할 점과 병행 가능한 작업을 제안 | 고정 게이트·일정 강제·개인 성과 코칭 |
| 개발 결정과 GitHub 작업·공유가 분리됨 | 승인된 Issue만 등록하고 선택한 작업물만 공유 | 자동 브랜치·자동 병합·전체 커밋 자동 공지 |

### 1.3 의사결정 요청

**현재 제품 기획의 기본 방향은 유지**한다. 본 문서에서는 사용자 흐름, 승인 경계, 정보 상태 정의, 오류·미확인 경험, 인수 기준을 명확하게 정리했다. 신규 개발 범위는 확정하지 않는다. 결정이 필요한 항목은 §11에 별도 등재한다. 특히 AI 의미 정확도 개선, 토큰 예산 보정, GitHub Project 실제 변경 검증은 기존 합의대로 기능 구현 완료와 분리한다.


## 2. 사용자·사용 환경·권한

### 2.1 대상 사용자와 핵심 과업

| 사용자 | 주요 목적 | 대표 행동 |
| --- | --- | --- |
| 일반 팀원 | 지난 맥락과 자신의 할 일·팀 결정 확인 | 질문하기, 진행상황 확인, 작업물 선택 공유 |
| 팀 조율 담당자 / 리더 | 다음 회의 논점·역할 간 조정·합의 관리 | 조율 제안 검토, 안건 보류·재개, 사람 작성 결정 등록 |
| GitHub 등록 승인권자 | 외부 시스템에 반영할 개발 작업 검토 | AI 이슈 제안 수정·제외·승인, 담당자 확인 |
| 지식 관리 담당자 | 오해석 정정과 기록의 추적 가능성 확보 | 탭에서 Markdown 수정·삭제·복원, 원문·이력 확인 |

**확정** GitHub 쓰기는 기존 권한 규칙(`people.can_approve`)을 따르며 사람의 명시적 승인 이후에만 실행한다. 위 사용자 구분은 과업 중심의 기획상 역할이며 별도 계정 권한 체계가 구현·승인됐다는 뜻은 아니다. 상세 권한 매트릭스는 §11에서 최종 확인한다.

### 2.2 접점 및 역할 분담

- **Teams 채팅 / Adaptive Cards:** 브리핑·질문·조율·개별 액션, 확인·승인과 결과 피드백.
- **Teams 탭:** 문서와 지식의 탐색·수정·이력·관계 확인. 새 SaaS 또는 별도 관리 앱을 만들지 않는다.
- **Notion:** 회의록·기획·조사 등 원본 출처. 읽기·변경 감지 대상이며 AI PM 탭 수정이 원본 Notion을 자동 수정하지 않는다.
- **GitHub:** 개발 Issue·PR·커밋·Project 작업 상태의 사실 출처. 사람 승인 이후에만 쓰기를 수행한다.

## 4. 핵심 사용자 시나리오 및 제품 동작

### S-01. 신규 팀 연결과 프로젝트 맥락 구축

**시작:** 팀이 Notion 자료를 처음 연결하거나 자료 구조가 바뀌었다.

**기대 동작:** 시스템은 페이지 계층·DB 속성·날짜·제목·최근 수정·링크의 메타 카탈로그를 작성하고, 최근 회의 자료를 우선 해석한다. AI가 카탈로그를 보고 추가로 읽을 기획·규칙·역할·조사 영역을 선택한다. 변경된 부분만 재해석하고 같은 내용은 캐시를 재사용한다.

**종료 상태:** 해석 대상에 포함된 산출물이 지식 항목·출처·관계와 연결된다. 제외한 영역은 미해석으로 남고, 질문 응답에서 조회 범위 밖임을 알린다. Notion 원본은 보존한다.

**예외:** 인용 불일치·모델 오류는 ‘팀이 결정해야 할 충돌’로 둔갑시키지 않고 기술 처리 상태로 남기며 재처리한다. 사람 수정은 덮어쓰지 않는다.

### S-02. 프로젝트 브리핑과 결정 변경 확인

**시작:** 팀원이 메뉴 1·2를 연다. 또는 “지난 요구사항 결정이 바뀌었어?”라고 질문한다.

**기대 동작:** 최근 문서와 결정·미정·작업 사실을 조합한다. 확정 기록은 그 근거를 표시하고, 가안·멘토 조언·논의는 확정과 분리한다. 이전 항목의 대체·해결·대안 관계가 있으면 관련 이력을 탐색할 수 있다.

**종료 상태:** 사용자가 ‘무엇이 확인됐고 무엇은 불확실한지’, ‘어디서 나온 정보인지’를 파악한다. 자료가 없으면 ‘조회 범위에서 확인되지 않음’으로 답한다.

**예외:** 최근 문서의 제목에 ‘최종’이 있다는 이유만으로 확정하지 않는다. 과거 문서와 충돌하는 경우 차이를 숨기지 않는다.

### S-03. 자연어 질문: 구현·작업 상태와 근거 위치

**시작:** “이 기능 구현됐어? 어디에 있어?” 또는 “발표의 주장은 어떤 자료가 근거야?”라는 질문.

**기대 동작:** 누적 지식 인덱스에서 관련 항목과 출처를 검색한다. 개발 작업 관련 질문이면 연결 가능한 GitHub Issue·PR·커밋 및 변경 파일 경로·상태를 조회한다. 명시 연결과 추정 연결을 구분한다. 질문할 때 Notion 전체를 다시 해석하지 않는다.

**종료 상태:** 답, 관련 원문·GitHub 링크, 확인한 정보의 범위, 확인하지 못한 내용을 함께 제시한다.

**예외:** `closed` Issue나 `merged` PR만을 근거로 실행·테스트·데모 검증이 끝났다고 말하지 않는다. 근거가 불충분하면 범위를 명시하고 판단을 유보한다.

### S-04. 팀 조율과 의사결정 기록

**시작:** 메뉴 2에서 ‘조율 보기’를 선택하거나 작업 방식의 대안을 질문한다.

**기대 동작:** AI는 현재 미정·충돌·작업·역할·의존 정보를 근거로 ‘지금 논의’, ‘나중에 논의’, ‘역할 간 조율’, ‘병렬 진행’ 항목을 제안한다. 상황에 맞는 Scrum / RAID / Product Discovery / Design Sprint / Spike 원문 기반 방법론 가운데 필요한 것만 참고한다. 팀원의 대안도 현재 방식과 비교하고 특정 프로세스를 강요하지 않는다.

**사람의 선택:** [다음 회의 안건으로] / [보류] / [결정 기록하기]. 사람의 직접 작성 문장만 결정 기록이 될 수 있다. 안건과 보류는 나중에 다시 열어 볼 수 있다.

**예외:** 조율 카드를 읽는 것만으로 결정·작업·외부 이슈는 생성되지 않는다. 현재 데이터에 의존관계가 없어도 AI가 조건부 제안은 할 수 있으나, 확인된 의존 사실로 표현해서는 안 된다. 해당 표현 정확도는 별도 품질 평가 항목이다.

### S-05. GitHub 개발 업무 제안과 승인

**시작:** 결정·요구사항에서 ‘이슈 제안’을 요청한다.

**기대 동작:** AI가 이슈 제목·본문·완료 기준·담당 후보를 제시한다. 권한자가 항목을 수정하거나 제외한 후 [등록]을 선택할 때에만 GitHub Issue를 생성·배정한다. 등록된 Issue만 저장된 할 일에 명시적으로 연결한다.

**종료 상태:** 등록 결과·대상 링크·실패한 항목의 이유를 카드에 표시한다. 중복 제출이 중복 생성으로 이어지지 않는다.

**예외:** 일부만 성공한 경우 성공한 결과만 연결하고 실패를 명확히 보여 준다. 사용자가 거절하거나 취소하면 외부 쓰기는 발생하지 않는다.

### S-06. 작업물 공유 및 GitHub 완료 동기화

**시작:** 메뉴 4에서 ‘작업물 공유하기’에 진입하거나 기존 완료 공유 기능을 사용한다.

**기대 동작:** 메뉴 진입 시 최근 PR·커밋 목록을 API로 조회한다. 사용자가 선택한 항목과 관련 지식을 바탕으로 공유 미리보기를 구성한다. [공유] 선택 시에만 Teams 메시지와 개발 산출물 근거를 남긴다. 프로젝트의 GitHub 완료 상태는 저장된 할 일의 진행상황과 일관되게 표시한다.

**종료 상태:** 선택한 작업물만 공유되며 기록에 원문 URL이 남는다. GitHub 완료 상태가 필요할 경우 ‘GitHub 완료’로만 표현한다.

**예외:** 취소·무응답은 공유와 지식 저장을 발생시키지 않는다. Project 동기화의 실제 실환경 경로는 별도로 검증해야 한다.

### S-07. 지식 검토·정정·복원

**시작:** 사용자가 Teams 탭에서 잘못된 요약이나 관계를 발견한다.

**기대 동작:** 문서·지식·소스 목록을 검색하고 원문·근거·관계·이력을 확인한다. 수정·논리 삭제·복원을 수행하면 검색과 후속 AI 입력에도 반영된다. 사람 수정 이력을 남기고 이후 재수집이 임의 덮어쓰지 못하도록 보호한다.

**예외:** 탭에서 고친 지식이 원본 Notion·GitHub를 수정하지 않는다. 대체·삭제된 항목에 열리지 않는 상세 링크를 생성하지 않는다.

### 5.1 주요 비즈니스 규칙 [확정]

1. **AI 제안은 그 자체로 팀 결정이 아니다.** 조율 화면에서 새 결정을 등록할 때는 사람이 직접 입력한 내용만 저장한다. 다만 원문에 명시적 합의가 기록된 경우에는 인용 근거를 조건으로 해당 합의 기록을 지식에 자동 반영할 수 있다.
2. **정보 부재는 부정의 증거가 아니다.** 검색 결과 없음은 조회 범위에서의 미확인이며, 해당 일이 실제로 없었다는 결론이 아니다.
3. **원문 인용 존재와 의미적 타당성은 다르다.** 저장 항목 ID·출처 링크의 유효성 검사만으로 AI 문장의 참을 보장하지 않는다.
4. **GitHub의 완료는 기능 검증이 아니다.** `Issue closed`/`PR merged`는 GitHub 상태로만 제시한다.
5. **자동 해석과 승인 기반 외부 쓰기는 서로 다른 통제 범위다.** 출처가 있는 문서 해석·관계 반영은 합의된 정책에 따라 자동 수행할 수 있으나 외부 Issue 등록·배정은 명시적 승인이 필요하다.
6. **기술 오류와 논의할 충돌을 구분한다.** 추출 실패·인용 불일치·LLM 한도 초과는 재처리 대상이고, 판단할 수 없는 중요한 내용 충돌만 팀 확인 대상이다.
7. **사람의 정정이 우선 보존된다.** 같은 근거 재수집만으로 사람의 수정·논리 삭제를 무효화하지 않는다.

### 5.2 상태 용어 정의

| 용어 | 의미 | 금지되는 오해 |
| --- | --- | --- |
| 가안(`draft`) | 아직 확정되지 않은 제시안 | 확정 결정 아님 |
| 권고(`recommended`) | 멘토·타인의 제안·권고 | 팀 합의 아님 |
| 논의(`discussed`) | 논의된 내용의 기록 | 결정 완료 아님 |
| 합의(`agreed`) | 명시적 합의 근거가 있는 기록 | 최신 문서/제목만으로 판단 불가 |
| 합의 상태 미확인 | 충분한 상태·근거가 기록되지 않음 | 합의하지 않았다는 뜻 아님 |
| 이슈 등록/진행/완료 | GitHub에서 확인한 개발 작업 상태 | 앱 기능 검증과 다름 |
| 추정 연결 | 문맥상 관련성을 모델이 추론한 연결 | 확인된 명시적 관계 아님 |
| 미해석/미조회 | 이번 분석의 대상에서 제외된 자료 | 해당 내용이 존재하지 않음과 다름 |


## 6. 화면·인터랙션 요구사항

### 6.1 Teams 카드의 정보 계층

**검토 제안** 기존 카드 구성 요소를 유지하되 화면 간 정보 우선순위를 통일한다.

- **상태 요약:** 팀원에게 필요한 한 문장, 현재 기준 시점과 범위.
- **핵심 내용:** 3~5개 이하의 핵심 항목을 우선 표시하되 항목 수 제한으로 제외한 건수는 표시.
- **근거와 한계:** 출처·링크·상태·명시/추정·미확인 범위를 사용자에게 해석 가능한 문구로 표시.
- **행동:** 열기/질문/안건/보류/결정/승인/취소 등 현재 문맥에 적합한 버튼만 노출.
- **작업 결과:** 버튼 이후 성공·실패·부분 성공, 생성한 외부 대상과 링크를 명확히 표시.

숫자형 표시 건수는 화면 설계 제안이며, 실제 카드 제한·UX 테스트 전 확정된 구현 상한이 아니다.

### 6.2 인터랙션 계약

| 상황 | 사용자에게 표시할 것 | 자동 수행 금지 |
| --- | --- | --- |
| AI 조율 제안 보기 | 제안·근거·방법론·대안 | 안건/결정 자동 등록 |
| 안건 보류 | 보류 상태와 재개 경로 | 결정으로 자동 승격 |
| 사람 결정 입력 | 입력한 문장과 보존 근거 | AI 문장으로 덮어쓰기 |
| 이슈 제안 | 항목별 포함/제외·수정·담당 | 승인 전 GitHub POST |
| 이슈 등록 부분 실패 | 성공 항목·실패 원인·재시도 범위 | 전체 성공으로 위장 |
| 작업물 공유 미리보기 | 선택 작업물·요약·링크 | 공유/지식 저장 자동 수행 |
| 자료를 찾지 못함 | 확인한 범위·미확인 이유·다음 탐색 행동 | 미구현·미결정 단정 |
| 출처 항목이 이동·삭제됨 | 원문 불일치/현재 링크 상태 | 유효하지 않은 상세 링크 표시 |

### 6.3 UX 인계 시 필요한 산출물 [검토 제안]

Teams 카드별 상태표(기본/로딩/빈 결과/권한 없음/부분 성공/실패), 버튼별 전이표, 모바일·데스크톱·Teams 탭 화면 캡처, 클릭 가능한 근거 링크 목록을 디자인·QA 인계물로 관리한다. 이번 문서에서는 새 카드 UI를 구현하거나 도안으로 확정하지 않는다.


## 7. 데이터·AI·외부 연동 원칙

### 7.1 데이터 수명주기

**원본 수집 → 해석 대상 선택 → 증분 해석 → 산출물/지식 축적 → 관계·상태 반영 → 검색·브리핑·조율 → 사람 검토/정정 → 수정 이력 보존.**

- **원본과 파생물 분리:** 원문 구간·문서 위치·변경 지문과 AI가 작성한 요약을 연결해 보존한다.
- **관계:** `DERIVED_FROM`, `ALTERNATIVE_TO`, `SUPERSEDES`, `RESOLVES`, `AFFECTS`, `RELATED_TO`를 상황에 맞게 표현한다. 관계의 존재만으로 의미적 타당성이 보장되는 것은 아니다.
- **유효성:** 논리 삭제·대체·해결 상태를 검색·표시·복원에 일관되게 반영한다.
- **조회 경계:** 질문은 인덱스와 해석된 지식 중심으로 응답한다. 미해석 소스가 있는 경우 그 범위를 밝힌다.
- **외부 시스템 원본:** AI PM의 지식 수정은 Notion·GitHub 원본을 수정하지 않는다.

### 7.2 AI 책임 분리

| 코드·시스템이 결정 | AI가 수행 | 사람에게 남는 결정 |
| --- | --- | --- |
| 조회 범위, 접근 권한, 상태값 검증, 검색, API 호출, 저장·이력·외부 쓰기 경계 | 문서 해석·정보 종합·질문 응답·팀 조율·Issue 분해안·공유 요약 생성 | 팀 합의, 확정 결정 입력, 외부 Issue 승인, 공유 실행, 잘못된 지식 정정 |

기능별 Markdown 지침과 JSON 출력 계약을 사용하며, 현재 설계는 Groq 우선·Cerebras 대체 호출을 활용한다. 별도 검증 모델의 상시 호출이나 새로운 멀티 에이전트 도입은 이 문서의 확정 범위가 아니다.

### 7.3 정확도·호출 성능의 독립 관리

**확정** 기능·카드·저장·외부 연동이 통과하는 것과, AI가 원문의 의미를 정확하게 보존해 답하는 것은 별개의 검증 축이다. 실제 LLM 오류 사례(합의 부재 단정, 근거에 없는 인과·중요도, 조율 대안 누락 등)는 폐기하지 않고 후속 A/B 평가 기준선으로 관리한다.

**[후속]** 원문 기반 평가 세트, 사람 판정표, 평가 지표·통과선, 구조 변경안 비교는 별도 승인·일정으로 수행한다. 토큰 추정치와 공급자 실측 차이의 보정도 별도 성능 개선 과제로 유지한다. 새 PRD가 정합성 설계 B를 구현 완료로 승격하지 않는다.

### 7.4 보안·안전 원칙

- 팀 범위가 다른 문서·작업·결정이 서로 섞이지 않아야 한다.
- 비밀 키·실제 회의 원문·개인 정보는 공개 저장소 테스트 픽스처와 오류 로그에 복사하지 않는다.
- 테스트는 실제 운영 데이터보다 격리 복사본을 우선한다. 외부 시스템 쓰기는 지정된 계정·대상·권한·승인 범위 안에서만 실행한다.
- GitHub POST·PATCH·Project 상태 변경 등은 승인 주체와 결과 링크를 추적 가능해야 한다.
- 실패·재시도·중복 제출 시 이중 기록과 저장소 불일치를 방지해야 한다.


## 8. 검증 전략 및 제품 인수 기준

### 8.1 검증 레벨 구분

| 레벨 | 목적 | 통과 의미 |
| --- | --- | --- |
| 단위·모킹 회귀 | 입력 계약, 분기, 권한·실패 처리 | 코드의 예상 경로가 재현됨 |

| Teams 수동 스모크 | 실제 메뉴·카드·버튼·탭·링크 확인 | 사용자가 주요 기능을 직접 실행할 수 있음 |
| 통합 E2E | Teams → 서버 → 지식 저장소 → GitHub 일관성 | 수직 사용자 시나리오가 연결됨 |
| AI 의미 평가 | 원문 대비 정확성·근거 일치·대안 보존 | 정해진 사람 판정 기준의 품질 수준 충족 여부 |

### 8.2 수동 점검 체크리스트

**검토 제안** 사용자가 최신 앱을 직접 눌러보는 것으로 v2.1 기능 구현 작업을 일단락할 때, 다음 시나리오는 기록해 두는 것이 좋다. 이는 모든 실제 통합 경로의 자동 E2E 통과를 뜻하지 않는다.

- [ ] 메뉴 1: 프로젝트 설명과 출처 링크 열림
- [ ] 메뉴 2: 확정/진행/불명확 및 조율 진입·안건 목록 표시
- [ ] 메뉴 3: 내 담당 작업과 GitHub 상태·링크 표시
- [ ] 메뉴 4: 개발 작업물 선택·미리보기·취소/공유 경로 확인
- [ ] 질문하기: 실제 질문·근거·범위·미확인 표시 확인
- [ ] 조율: 제안 → 안건/보류 → 재개 → 직접 입력 결정 동작 확인
- [ ] 지식 탭: 검색, 상세, 수정, 복원, 출처·이력 이동
- [ ] 승인 카드: 미승인 상태에 외부 쓰기가 발생하지 않음
- [ ] 기록: 테스트 대상, 시각, 버전, 실제 결과, 문제 여부 남김

**유의:** 실제 팀의 기존 지식 기록이 남아 있는 저장소에서 수행할 때는 쓰기 테스트 범위를 구분한다. 무상태 탐색은 사용자 수동으로 확인할 수 있지만, 테스트용 결정·이슈·지식 기록 생성은 실제 데이터 오염을 피하기 위한 통제가 필요하다.

### 8.4 일단락 판정 [검토 제안]

- **기능 개발 일단락:** 사용자 수동 스모크에서 핵심 화면이 정상 동작하고 차단급 오류가 없으며, 미검증 영역을 기록한 상태.
- **제품의 정식 운영 적합성:** 실제 권한·데이터 일관성·권한 격리·관측·오류 처리와 품질 기준이 별도로 충족되어야 판단 가능. 현재 보고만으로 ‘정식 운영 검증 완료’라고 표기하지 않는다.
- **AI 의미 품질:** 후속 A/B 및 사람 판정 전에는 ‘미평가/오류 사례 확보’로 유지.


## 9. 품질 속성과 비기능 요구사항

| 품질 속성 | 요구사항 | 측정·확인 기준 |
| --- | --- | --- |
| 추적 가능성 | 상태·조율·질문이 가능한 한 원문과 작업 사실에 연결 | 출처/링크/상태/조회 범위 표시 검사 |
| 일관성 | 메뉴·QA·탭의 의사결정 상태 표시가 모순되지 않음 | 동일 데이터에 대한 상태 표기 교차 비교 |
| 안전한 쓰기 | 승인 없는 외부 Issue·Project 상태 변경 금지 | 무응답/취소/권한 없음 회귀 |
| 복원 가능성 | 사람 수정·논리 삭제 및 변경 이력을 보존 | 재수집·복원 시나리오 |

| 접근성·가독성 | Teams 카드가 좁은 화면에서도 이해 가능 | 실제 Teams 데스크톱/모바일 확인 필요 |

**결정 필요** 구체적인 성능 SLA(예: 95백분위 응답시간), 의미 정확도 목표, 데이터 보존 기간 및 사용자 역할별 세부 권한은 현재 자료만으로 승인된 수치를 정할 수 없다. 개발·QA가 임의로 숫자를 채워 통과 판정하지 않도록 §11에서 결정한다.


## 10. 이관 범위 및 후속 로드맵

### 10.1 v2.1 사용성 마무리

**사용자 직접 Teams 스모크 테스트 → 차단급 문제만 이슈화 → 현행 기능 일단락**의 운영 방침을 따른다. 테스트 과정에서 새로운 기능을 요구하지 않는다. 기록과 증빙이 부족한 항목은 ‘미검증’으로 표기한다.

### 10.2 별도 품질·운영 트랙

### 10.3 인계 산출물

제품 책임자에게는 본 PRD와 결정 대기 목록(§11)을 전달한다. 디자인팀에는 §3·§4·§6의 정보 구조·상태별 UX 요구를, 개발팀에는 §5·§7의 업무 규칙과 데이터·승인 경계를, QA에는 §8·§9의 수용 기준과 미검증 항목을 전달한다. 기존 구현에 대한 실제 함수·스키마 수준의 명세는 `plan.md` 및 작업 트리의 현행 코드가 우선하며, 본 문서를 근거로 코드가 이미 수정됐다고 판단하지 않는다.
