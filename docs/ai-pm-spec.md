# AI PM 통합 요구사항 및 Claude Code 구현 계획 도출 지시

> 목적: 지금까지 합의한 제품 경험과 설계 원칙을 확정된 요구사항으로 전달한다. **이번 요청은 구현이 아니라 코드 대조 및 실행 가능한 구현 계획 도출**이다.
> 검토 대상: 현재 열려 있는 AI PM 저장소 / Build-log `C:\Users\aicam\Desktop\build-log`
> 작업 권한: **읽기 전용**. 코드, DB, 설정, Notion, GitHub, Teams 및 외부 서비스의 상태를 변경하지 않는다.

## G — Goal

기존 Microsoft Teams 기반 AI PM을 **프로젝트 전체의 맥락을 이해하고 팀 간 의사결정과 작업 흐름을 조율하는 AI PM**으로 정렬할 최소 구현 계획을 도출해 줘.

단순 단계·게이트 관리, 개인별 업무 코칭, 문서 요약기, GitHub 변경 알림 봇이 목표가 아니다. 기획·시장조사·디자인·개발·발표·운영 전반의 산출물을 연결하여, 팀원이 현재의 합의와 진행상황을 확인하고 **지금 정할 사항 / 나중에 정할 사항 / 역할 간 조율할 사항**을 판단할 수 있게 해야 한다.

핵심 사용자 경험은 다음과 같다.

1. **프로젝트 리딩:** 최근 회의와 실제 산출물을 종합하여 프로젝트가 어디까지 왔고 어떤 결정·문제가 중요한지 설명한다. 단계·게이트는 필요할 때 참고하되 UX와 LLM 판단의 중심으로 강제하지 않는다.
2. **프로젝트 맥락 축적:** 흩어지고 가안도 많은 Notion 자료에서 현재 맥락을 찾아, 원문·요약·중요 지식·근거·관계·이력을 점진적으로 축적한다.
3. **팀원 간 자연어 확인:** “이 기능 구현됐어? 어디에 있어?”, “저번 요구사항 결정됐어?”, “발표의 이 주장은 어떤 자료에 근거해?”에 대해 접근 가능한 자료를 조사하여 **확인 내용·근거 위치·조회 범위·미확인 사항**을 답한다.
4. **팀 전체 조율:** 회의에서 정한 내용과 현재 작업 의존성을 보고 지금 함께 결정해야 할 사안, 나중에 정해도 될 사안, 병렬 진행과 역할 분배를 제안한다. 팀원이 다른 진행 방식을 제시하면 적절한 실무 레퍼런스를 참고하여 대안을 검토하되 프로세스를 강요하지 않는다.
5. **업무 연동:** 개발 업무는 AI가 GitHub Issue 분해·담당 배분을 **제안**하고 사용자가 검토·수정·승인한 것만 실제 등록한다. GitHub 작업물 공유는 기존 Teams **'작업물 공유하기' 메뉴에서 사람이 골라 공유**한다. 비개발 업무에 GitHub Issue를 강제하지 않는다.
6. **지식 관리 대시보드:** 축적된 Markdown 지식은 **기존 Teams 탭 화면**을 대시보드로 사용하여 조회·검색·수정·삭제(논리 삭제 우선)하고, 출처·관계·이력을 확인할 수 있어야 한다. 수정 사항은 이후 검색과 LLM 판단에 반영한다.

## C — Context / 합의한 운영 원칙

### 1. 현재 코드에 관한 기존 읽기 전용 조사 결과 (반드시 재검증)

- AI PM에는 Notion 수집·메타구조/부분별 Markdown·출처/인용·`sources`/`evidence`/`revisions`·일부 관계·자동 반영/되돌리기·Teams 메뉴/Adaptive Cards·기존 탭·GitHub 이슈 조회/배정/Project 상태 변경·LLM 큐/캐시가 일부 구현돼 있다고 보고되었다.
- 회의록은 항목 추출이 가능하나 일반 문서(PRD, 시장조사, 발표 등)는 수집 후 충분히 해석되지 않는다. 지식 검색/질의 응답 경로와 산출물 간 관계 추적은 부족하다. 게이트·단계 판단과 UI가 과도한 비중을 차지한다.
- 최근 조사에서는 `gpt-oss-120b`를 Groq 우선·Cerebras 대체로 호출하고 JSON 단일 응답 방식으로 사용한다고 보고되었다. 현재 앱의 입력·출력 예산/큐 제한을 확인하되 이를 모델의 절대적인 컨텍스트 한계로 오해하지 말 것. 무료 한도와 호출 비용을 고려한다.
- Build-log에는 Markdown 본문·요약, 출처 및 위치 인용, 지식 상태, 관계/이력, `prior_check`, FTS5 색인, 관련 기록을 예산 안에서 조회하는 방식 등이 있다고 보고되었다. **실제 구현을 확인하고 재사용 가능한 패턴을 찾아라.** 통째로 이식하는 것을 전제하지 않는다.
- 기존 GitHub 연결 저장소가 테스트용 `n8nTest`일 가능성이 보고되었다. 실제 연동 대상과 권한은 확인 사항으로 분리한다. Jira/Figma/슬라이드 본문/Clova 등은 현재 연동 여부가 불확실하거나 미구현인 것으로 보고되었다. 구현되어 있다고 가정하지 말 것.

### 2. Notion 탐색·지식 축적 방식 (중요)

Notion은 처음부터 일관된 정답 데이터베이스가 아니다. 정리가 안 된 문서, 잘 정리됐지만 **가안**인 문서, 현재 쓸 만한 근거가 혼재한다.

- 초기 파악 시 **최근 회의록을 먼저 읽어 현재 논의 맥락을 잡는다.** 그다음 Notion의 페이지 계층·DB 스키마/속성·제목·날짜·링크 등 **메타구조**를 훑어 팀 규칙·프로젝트 목표·PRD·팀 역할과 관련 조사/이전 회의 자료를 **선택적으로** 읽는다. 고정된 페이지명이나 정해진 자료 세트를 전제하지 않는다.
- 이후 회의록·기획 변경·조사 결과·개발/디자인/발표 산출물 등 새로운 진행 기록을 기존 맥락과 **조각모음하듯 점진적으로 연결**한다.
- 원본과 그 출처는 보존한다. 산출물별 Markdown 본문/짧은 요약과 중요한 결정·요구사항·가설·미정·후속 작업 등을 추출하되, 모든 문장을 정형 항목으로 쪼개지 않는다.
- 새 정보가 이전 정보를 보완·대체·해결·충돌하는지 판단하고 이력/근거를 남긴다. 가안·권고·회의 논의·합의/확정·작업 등록·PR 병합·구현 검증은 서로 혼동하지 않는다. 최신 수정일이나 `최종`이라는 제목만으로 확정 여부를 단정하지 않는다.
- **평소 질문할 때는 축적된 지식 DB/색인에서 검색하는 것이 기본이다.** 매 질문마다 Notion 전체를 다시 훑지 않는다. 초기 탐색과 변경 감지/증분 반영을 기본으로 하고, 원본 변경·수집 누락 등 구체적인 이유가 있을 때만 관련 원문 갱신을 검토한다.
- Build-log처럼 Markdown은 사람과 LLM이 읽기 좋은 지식 표현이고, **빠른 검색은 DB 인덱스/메타데이터/관계**로 해결한다. 저장된 요약만 보고 단정하지 말고, 필요하면 원문 구간과 근거를 다시 연결할 수 있어야 한다.

### 3. 기능별 Groq LLM 지침

- **메뉴·하위 기능별로 LLM의 역할이 달라야 한다.** 해당 역할을 Markdown 지침으로 관리하고 기능 호출 시 필요한 지침을 조합한다. 공통 근거/출처 규칙은 공유해도 되지만, 임의로 `PM 역할 세 개`로 제한하지 말 것.
- 예: 프로젝트 정보 설명, 프로젝트 리딩, 팀 간 자연어 질의응답, 팀 조율/의사결정, 이슈 분해·분배 제안, 선택된 작업물 공유용 정리, 회의록·일반 산출물 해석. **실제 메뉴와 호출 코드에 매핑하여 필요한 파일만 제안**한다.
- 지침 Markdown은 **판단 방법**이고 Build-log식 Markdown/DB는 **판단 대상인 프로젝트 지식**이다. `AGENTS.md` 또는 역할별 독립 에이전트는 필수가 아니다. Markdown 파일을 Groq API가 자동으로 읽지는 않으므로 서버가 명시적으로 로드/조합해야 한다.
- 초기는 단일 Groq 모델을 우선 활용한다. 도구 호출/멀티 에이전트는 필요성·호출량·안정성을 검증하기 전까지 도입하지 않는다. 단순 조회/동기화 등은 코드로 처리하고, LLM은 자료 해석·종합 판단·조율안·답변 생성에 집중한다.

### 4. 팀 간 질의응답: 검색 가치와 추적 한계

- Teams의 **메뉴 진입 후 자연어 질문**을 이번 핵심 기능에 포함한다. 자연어로 외부 시스템을 수정하는 명령 기능까지 열자는 뜻은 아니다.
- Notion 기반 지식에서 요구사항·결정·조사 근거를 찾고, 구현/작업 상태에 관한 질문이면 **필요한 경우에 한해** GitHub 이슈·PR·커밋·변경 파일·코드·테스트 등 실제 산출물을 조회한다. GitHub가 모든 프로젝트 산출물의 유일한 출처는 아니다.
- GitHub의 실제 검색 가능 범위·연동 저장소·권한을 검증해 검색 경로를 제안한다. 명시적 이슈/PR 연결과 의미상 추정된 연결을 구분한다.
- 답변은 가능하면 **어디에 있는지**(Notion 문서/섹션, GitHub Issue·PR·파일 경로 등)를 제공하고, 찾지 못했으면 **어떤 범위에서 찾지 못했는지** 설명한다. 발견하지 못한 것을 미구현·미결정으로 단정하지 않는다.
- PR 병합/이슈 종료, 실제 코드 존재, 테스트 통과, 데모 시연 가능은 서로 다른 사실이다. 구체적인 근거 없이 구현 검증을 확정하지 말 것.

### 5. 팀 조율 및 GitHub 작업 운영

- AI는 멘토형 **팀 전체 PM/Facilitator**로서 지금 필요한 합의, 뒤로 미룰 결정, 역할 간 의존성, 병렬 진행 방안을 제시한다. 개인에게 업무를 나열하거나 모든 결정을 게이트로 강제하지 않는다.
- 예: MVP 단계에서 핵심 시나리오/기능 범위가 불분명하여 디자인 와이어프레임과 데모 개발이 엇갈린다면, 꼭 필요한 최소 합의를 제안하고 나머지는 병렬 진행하도록 조율한다. 개발자가 `만들면서 QA`를 제안하면 해당 실무 방식과 트레이드오프를 근거로 검토한다.
- AI가 개발 이슈를 쪼개고 담당/완료 기준을 **제안**한다. 팀원이 검토·수정·승인한 것만 GitHub Issue로 등록/배정한다. 실제 GitHub 쓰기는 구현 단계에서 권한·승인·실패 복구를 검증해야 한다.
- 브랜치는 **`main` + 필요할 때 짧은 작업 브랜치 + PR 병합** 정도의 약식 GitHub Flow를 우선한다. 이슈별 자동 브랜치 생성/복잡한 Git Flow/자동 병합은 초기 범위가 아니다.
- GitHub Actions 등으로 감지한 변경사항을 목록화하는 것과 **'작업물 공유하기' 메뉴에서 팀원이 선택해 공유하는 것**은 분리한다. AI가 모든 커밋을 자동 Teams 공지로 발송하지 않는다. 공유된 작업물은 이후 프로젝트 맥락의 근거로 활용할 수 있다.
- 비개발 업무는 GitHub Issue 사용을 강제하지 않는다. 전체 팀 조율과 개발 저장소의 작업 운영은 구분한다.

### 6. 기존 Teams 탭 = 지식 관리 대시보드

- 이미 마련한 **Teams 탭 화면(탐색기/문서·소스/관계·이력 등 실제 구현 확인)**을 프로젝트 지식 대시보드로 연결한다. 새 SaaS나 별도 관리 웹앱을 만들지 않는다.
- 저장된 Markdown 지식의 **목록·검색·본문/출처 조회, 수정, 삭제/비활성화, 변경 이력과 복원**을 지원해야 한다. 문서 자체와 핵심 지식 항목 및 관계 수정 범위는 기존 UI와 데이터 모델을 확인해 최소로 제안한다.
- 사람이 수정한 내용이 **인덱스와 후속 Groq 판단**에 반영되어야 하며, Notion 재수집으로 무조건 덮어쓰면 안 된다.
- **원본 Notion/GitHub 자료는 보호**한다. AI PM의 지식 수정이 원본 외부 소스를 자동 변경하지 않도록 한다. 삭제는 복원 가능한 논리 삭제를 우선 검토하고 출처 이력을 보존한다.
- Teams 채팅·Adaptive Cards는 프로젝트 리딩/질문/조율/업무 선택의 기본 인터페이스이고, 탭은 지식 관리·검토 인터페이스다.

## B — Boundaries / Claude Code가 이번에 도출할 것

현재 AI PM 코드와 Build-log 실제 구현을 읽기 전용으로 대조하고, 아래 **구현 가능한 계획**을 만들어 줘.

1. **As-Is 기능 매핑:** 실제 Teams 메뉴·하위 기능 → 사용자 경험 → 현행 라우트/프롬프트/LLM 호출/DB·외부 연동을 표로 정리. `구현 / 부분 구현 / 미구현`을 근거 파일·함수·라인과 함께 표시. 기존 탭의 현재 조회·수정·삭제 동작도 확인.
2. **구조 재사용 제안:** Build-log의 Markdown 본문·요약·메타데이터·인용·`prior_check`·관계/이력·FTS5 조회 중 무엇을 AI PM의 기존 `sources`·`evidence`·`revisions` 등에 재사용할 수 있는지 구분. 새 테이블·관계 타입은 **꼭 필요한 경우에만** 제안하고 데이터 마이그레이션/충돌 방지까지 검토.
3. **Notion 초기 탐색/증분 통합:** 최근 회의록을 출발점으로 메타구조 기반 관련 자료를 선별하는 방법, 신규 자료를 기존 지식과 연결하는 방법, 출처·가안·확정/유효성 처리, 중복·충돌·사람 수정 보호 방법. **LLM 호출/토큰 예산을 고려한 실제 구현 경로** 제안.
4. **메뉴별 Markdown 지침 매핑:** 현재 메뉴와 필요한 신규 질의 기능에 대해 실제 LLM 책임·입력 근거·출력 JSON·호출 트리거를 매핑. 지침 파일 트리와 기존 코드 프롬프트의 이관/공유 관계를 제안. 하나의 메뉴를 무조건 한 번 호출하도록 만들거나 반대로 파일마다 API를 호출하도록 만들지 말 것.
5. **핵심 동작 수직 검증 시나리오:** (a) 최근 회의→PRD/조사·피드백을 연결해 현 상태 판단, (b) 자연어로 결정 변경 여부 조사, (c) 자연어로 기능 구현 위치/시연 근거 조사, (d) 지금/나중 의사결정 분리와 역할별 조율안, (e) 승인된 개발 이슈 생성/배분과 작업물 선택 공유, (f) 탭에서 Markdown 정정/삭제 후 검색·LLM 반영. 각 시나리오의 필요 소스·현행 단절 지점·완료 기준을 제시.
6. **구현 WBS:** 기존 코드 최대 재사용을 전제로 단계별 작업, 선후행 의존성, 예상 난이도/작업량, 완료 기준, 검증/회귀 테스트를 작성. 우선순위는 **사용자가 실제 경험할 수 있는 기능의 수직 완성**을 기준으로 제안. 확정된 기능/후속 연동 범위를 구분한다.
7. **불확실성·리스크:** 현재 Groq·Cerebras 실측 사용량/한도, 검색 정확도, GitHub 저장소/권한, PR·코드 조회 범위, Notion 소스 혼재, 데이터 재수집과 사람 수정 충돌, 인용 검증 및 탭 CRUD 복구 가능성을 실제 근거로 명시. 확인하지 않은 사항은 확인한 것처럼 서술하지 않는다.

### 작업 금지 및 범위

- **이번에는 조사와 계획만 수행.** 파일 작성·코드 수정·DB 마이그레이션·API 쓰기·GitHub/Notion/Teams 상태 변경·실제 이슈 등록 금지.
- 새로운 SaaS, 복잡한 게이트 엔진, 전면 DB 교체, 멀티 에이전트, 브랜치 자동 운영을 전제로 하지 말 것.
- Notion을 사전에 완벽하게 정형화하거나 검색할 때마다 전체 문서를 재수집하지 말 것.
- 사람의 승인 없이 AI 제안을 확정 결정이나 실제 작업으로 자동 반영하지 말 것.
- 이미 운영 중인 기능·메뉴·탭을 최대한 유지하되, **합의한 사용자 경험과 충돌하는 부분**은 이유를 제시해 수정 계획에 포함한다.
- 구현 방식을 과도하게 선결정하지 말고, 각 후보의 트레이드오프와 **추천 최소안**을 근거와 함께 제시할 것.

**출력 형식:** `① 핵심 결론 ② As-Is/Gap ③ 권장 최소 구조(데이터·탐색·LLM·UI) ④ 메뉴별 역할 매핑 ⑤ 시나리오별 검증 ⑥ 우선순위 WBS·완료 기준 ⑦ 확인이 필요한 결정`. 불필요한 일반론보다 파일 경로와 실제 코드 근거를 우선해 줘.
